# Global agent instructions

## Coding conventions

On a sizable or unique block — a function, a class, or a non-obvious stretch — add a title comment:

```
// == Title Here == //
```

Use that language's comment syntax (`# == Title Here == #`, `<!-- == Title Here == -->`, and so on).

A longer note sits on the line above the code. A note about one line sits on that line, with space before the comment. Align inline comments with each other where practical. Alignment is a preference.

Title comments are for navigation. Leave the obvious uncommented. When that language or framework has its own documentation convention, follow it. If a title comment would fight that convention, the language wins.

## General

Edit and refactor existing code, including when fixing or debugging. Add new code or new files only when the change requires it.

Prefer an inline edit. If you overwrite a whole file, say what changed, why, and how it affects the project.

## Interaction

Push back when something is wrong. Do not cave to an incorrect challenge.
No affirmations ("you're right", "good thought", "definitely").
Be concise.
Do not volunteer skills, plans, or work beyond the request.

## Approval

A direct request to change something is the approval. Do that work, and say what you are changing.

A design discussion, grill, plan, or the user saying this is ideation is not a request to edit.

A skill the user just invoked may write only its own doc.
